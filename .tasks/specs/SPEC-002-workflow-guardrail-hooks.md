# SPEC-002: Workflow guardrail hooks

## Problem

Every skill in this toolkit states its guardrails as prose an LLM is expected to follow: never
hand-edit a `BEGIN:`/`END:` region, never hand-edit an epic's `status` except to `wont-do`, never
`gh pr merge`, force-push only `--force-with-lease` on the task's own branch, run
`test_command`/`lint_command`/`format_command` before a PR. Compliance today is **probabilistic**
— nothing actually stops a violation, it only gets caught (or doesn't) by whoever reviews the
diff. Claude Code's hooks mechanism (`PreToolUse` deny, `.claude/settings.json`) can make the
mechanically-checkable subset of these **structural** instead: the tool call is refused before it
runs, every time, regardless of what the model decides to do.

Hooks are per-project config, exactly like the skills — `init-project` scaffolds them into a new
repo and `upgrade` keeps them current, the same way `.claude/skills/*` and `.tasks/config.md` are
handled today.

Key finding that shapes the design: `PreToolUse`/`Bash` hooks only see commands run *as a tool
call*. Once `implement-task`'s git/gh actions move into a Python script, a hook watching for
`git push` would never fire, because the model's tool call is `python3 .../implement-task.py
phase3`, not `git push` directly. So a hook enforcing "don't force-push the wrong branch" and the
script's own obligation to enforce that same rule are two enforcement points for the *same*
rules, not competing designs — the hook is the backstop for when the model bypasses the script and
runs `git`/`gh` by hand; the in-script check is what fires on the normal path.

## Goals

- Move every mechanically-checkable guardrail and pre-PR requirement from skill prose into
  `PreToolUse` hooks that structurally deny the violating tool call.
- Ship hooks per-project via `init-project`/`upgrade`, exactly like the skills.
- Define guardrail logic once, in a shared stdlib module, reused by both the hooks and the
  skills' own scripts — never duplicated.
- Cover the full `SPEC-001 §Guardrails` list, the pre-PR quality gates (`test_command`,
  `lint_command`, `format_command`, `sync check`), a repo-only scan for leftover
  `SPEC-NNN`/`TASK-NNN` references in the portable surface, and keep `upgrade`'s excluded-files
  guarantee intact once hooks exist.

## Non-goals

- Not replacing the skills' STOP/approval flow. Hooks are a backstop for mechanical violations,
  not a substitute for judgment calls (sizing a task, deciding a stale task's fate, approving a
  plan). Nothing here removes an existing STOP.
- Not a general-purpose hook framework. Scope is this workflow's own guardrails and gates — not a
  reusable "hooks toolkit" for arbitrary project rules.
- Not covering hook events unrelated to this workflow (model switches, subagents, notifications,
  etc.).
- Not auto-fixing and committing on the model's behalf. The pre-PR gate denies and reports; it
  never mutates the tree itself — this matters most for the formatter, whose changes must land in
  the PR's own commit, not be silently added by a hook.

## Alternatives considered

- **Status quo (skill prose only).** Rejected — it's exactly the probabilistic-compliance problem
  this spec exists to fix.
- **Enforce only inside each skill's own script**, once the script-extraction tasks land, with no
  hooks at all. Rejected — it only catches a violation when the agent goes through the script; it
  does nothing if the agent runs `git`/`gh` directly or hand-edits a region file.
- **Enforce only via hooks**, dropping the "enforce in the script" requirement from the
  script-extraction work. Rejected — a script that doesn't check its own preconditions still
  needs somewhere to look the rule up; two independent implementations of "is this branch allowed
  to force-push" is a guaranteed drift source. A shared module is strictly better than either
  extreme.
- **A hook that auto-fixes** (runs the formatter and commits, fixes lint) rather than
  deny-and-report. Rejected — a hook silently rewriting and committing behind the agent's back is
  hard to reason about and can surprise a human mid-review; deny-with-instructions keeps the
  agent's own commit as the record of what changed.
