# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A design-stage repo for a reusable, LLM-driven SDLC workflow: "kanban in markdown" for
solo, single-repo projects. There is **no application code, build, lint, or test setup
yet** — the artifacts here are markdown. The eventual deliverable is a set of Claude Code
skills plus templates that will be extracted into a standalone workflow repo.

## Key files

- `README.md` — the workflow concept and the current `TASK-*.md` prose format.
- `project-management-plan.md` — **the roadmap.** A critique of the README's workflow with
  concrete decisions on the data model, skill breakdown, and build sequencing. When
  implementing anything here, this file is the spec; the README describes the older design
  it supersedes.
- `.tasks/BOARD.md` — the kanban board (sections: TODO / In Progress / Blocked / Done /
  Won't do).
- `.tasks/TASK-*.md` — one file per task (none exist yet).

## Design decisions already locked in (from `project-management-plan.md`)

- Every `TASK-*.md` gets **YAML frontmatter** (`id`, `title`, `type`, `status`, `created`,
  `branch`, `pr`, `blocked_by`, `blocks`). Frontmatter — not prose — owns `status` and
  block relationships.
- **Task-file frontmatter is the single source of truth for status.** `BOARD.md` owns only
  the TODO priority ordering (human-maintained). Everything else in `BOARD.md` is meant to
  be regenerated by a deterministic `sync` script — do not hand-edit the two to match.
- Determinism over model judgment for: board regeneration, ID allocation (`max existing ID
  across .tasks/ and .tasks/archive/, +1`), archiving `done`/`wont-do` into
  `.tasks/archive/`, and computing blocked status.
- The "implement a ticket" skill is split into checkpointed phases (Start / Implement+test
  / Wrap up / Merge) with human approval between them; never auto-merge to `main`.
- Generic skill logic is kept separate from per-project config (a `.tasks/config.md` with
  `test_command`, `lint_command`, `default_branch`, etc. plus a `workflow_version`).
- Terminology: use **"task"** consistently (the README mixes "task"/"ticket").

## Build order (from the plan)

Data model → `sync` script + `config.md` schema → skills in order `init` → `add ticket` →
`implement a ticket` (phased) → `backlog refinement` → `requirements gathering` → dogfood
on this repo → extract into the standalone workflow repo.
